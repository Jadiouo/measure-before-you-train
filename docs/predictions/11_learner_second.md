依據（全部來自第一份 log）：
1. 第一份 log：所有 9 個 run 在 update 0 的熵都是 0.088–0.094（解析式：偏置 +5 時，3 或 4 個動作的熵為 0.08–0.12），取樣換位數約 5.3（每回合）。
2. 第一份 log 中塌縮的 run（c10 格種子 0：熵 0.003–0.004、換位數降到約 0.6–1.0、貪婪 F≈−1.8）熵單調下降，從未回升；其他種子的熵維持 0.008–0.13。c1 格（換位便宜）熵 0.25–0.47，沒有塌縮。（推論：初始「不動」機率 ≈0.98，早期更新中換位動作很少被取樣到，換位的優勢估計雜訊大，個別種子容易把換位壓成 0。）
3. 解析式：+2 時 3 動作熵 0.67、4 動作熵 0.92（「不動」機率 0.71–0.79），初始換位機率約 21–29%，比 +5 的約 1–2% 高一個量級以上。+2 是〔作者〕建議的數字之一，**不做 +1、+3 的比較**。
4. **不動 ent_coef**：第一份 log 沒有任何證據能說明改 ent_coef 會比改初始熵更好，同時改兩個會分不清是哪個起作用；保持 0.01。
5. 種子 3→5：只為縮小 CI（第一份各格 CI 寬度 ≈2，主要由逐種子差異決定）；不是修探索，也不改判準。

副作用（推論）：+2 的初始策略會做很多無謂換位（耗電），初始航程比會比 +5 的 1.03 低，學習早期要先學會「少換」；這是可接受的代價，也可能讓所需 U 變大，所以階梯照第一份。

程式改動：只在 scripts/l3_mappo_vmap.py 加命令列參數 `--none_bias`（預設 5.0 = 第一份值，不給參數時行為與第一份逐位元相同）並把它寫進輸出 JSON；scripts/l3_mappo.py（演算法本體，其 `--none_bias` 參數本來就有）、drone_l3_jax.py、l3_cells.py、l3_analyze.py、tests 全部未改，sha256 與第一份第 8 節相同。

## 3. 預測（跑之前）

- 正向對照通過：U=500 通過 10%；U≤1000 通過 25%；U≤2000 通過 35%。（推論：第一份非塌縮種子的 F 只有 0.3–0.5，即使完全消除塌縮，種子平均也只在門檻 0.5 附近；塌縮是否真由初始熵引起未經測試。）
- 通過與否的 F_G 點估計：U=2000 時三格 F_G 的中位數 **0.35**（80% 區間 0.0–0.7）；至少一格出現「塌縮」種子（熵 <0.01 且該種子 F_G <−1）的機率 30%。

- **打臉條件**：(a) U=500 就通過（我高估了難度）；(b) 15 個 run（3 格×5 種子）在 U=2000 中仍有 ≥2 個塌縮（熵 <0.01 且 F_G <−1）→ 「塌縮來自初始熵太低」的診斷被打臉，缺口不在探索；(c) 15 個 run 全部 F_G>0 但 3 格中通過 <2 格 → 探索修好了，但優化（預算／門檻）不夠，不是塌縮問題；(d) 通過但 F_G 點估計 ≥0.9 → 我高估了難度。
