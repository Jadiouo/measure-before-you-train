# 預測：Haiku 與 Sonnet 當 LLM 指揮官（寫於跑任何 LLM 之前）

日期 2026-11-02。環境：L1，N=7、V 形、最佳設定、f=0.4、c=3、個體差異 ±15%、64 個固定種子。14 條指令，見 instructions.json。
指標：valid（JSON 合 schema）、constraint_ok（硬限制，程式判定）、regret = (oracle - 航程比)/oracle。
我只看過 oracle 的整體量級（環境裡好規則與壞規則差約 0-20%），沒有看過任何 LLM 輸出。

## 一個先決觀察
環境裡限制多半不貴：幾乎所有條件下，最佳規則都是 gate（任期 1、餘裕 5-40），oracle 與無限制最佳相差 < 0.1%。所以 regret 主要來自「挑錯規則類型」（time 或 rot 會比 gate 差 6-20%），而不是限制本身的代價。

## 預期（點估計，括號為範圍）
| | Haiku | Sonnet |
|---|---|---|
| 輸出有效（valid）| 93%（80-100%）| 100%（93-100%）|
| 硬限制遵守率（14 條中 constraint_ok；矛盾條以滿足任一解讀計）| 71%（50-86%）| 86%（71-100%）|
| 其中「寫在 no_lead / max_swaps 這類明講欄位」的條目（c2 c3 t4 c6 t9）| 90% | 100% |
| 全部條目 regret 中位數 | 4%（0-12%）| 1%（0-5%）|
| 全部條目 regret 平均 | 6%（2-12%）| 2.5%（0.5-6%）|

## 哪類指令會錯
1. 明確的機號限制（c2、c6）：兩個模型都會填 no_lead，遵守率高。Haiku 偶爾忘記某一個機號（c6 兩個機號只填一個），機率約 15%。
2. 換位次數上限（c3、t4、c6、t9）：會填 max_swaps，但常搭配 time 或 rot（「少換位」被理解成「定期輪替但少一點」），所以 constraint_ok 大致成立、regret 會偏大。Haiku 在 t4（最多 1 次）與 t9（零次）上傾向選 rot/time 並把 tenure 拉大而沒填 max_swaps（約 25% 機率違規）；Sonnet 較會用 fixed 或 max_swaps=0（約 8%）。
3. 保護／電量（p5、p8、v12）：schema 的 protect 語意（鎖在最省位置、不換位）模型可能不採用，改填 no_lead。遵守判定是看剩餘電量比全隊平均多 0.015，在這個環境中 no_lead 也常剛好過關，所以違規率低（Haiku 20%、Sonnet 10%），但 p8 的「航程不低於 90%」大概都過。
4. 比例型限制（s7：4 號機領頭 <= 10%）：最容易漏的一條。「不超過 10%」看起來要精算，模型多半直接 no_lead=[4]（這樣正確）；少數用 gate 並期望它自然少領頭而違規。預期 Haiku 違規 30%、Sonnet 15%。
5. 全員輪流領頭（t10、x13、x14 的輪流解讀）：需要 rot 或 time，且 max_swaps >= 6、tenure 夠小讓每架都輪到。常見錯誤是 tenure 太大（如 100），在電池耗盡前輪不完 7 架。預期 Haiku t10 違規 40%，Sonnet 20%。
6. 模糊（v11、v12）：只要選任一合理解讀就算遵守，遵守率接近 100%；regret 取決於它選哪個。預期兩者都選「少換位」解讀。
7. 矛盾（x13、x14）：模型會選一個解讀；Sonnet 在 notes 點出衝突的機率約 85%，Haiku 約 55%。Haiku 較可能試圖同時滿足（rot + max_swaps=0 之類不一致組合），導致兩個解讀都不滿足（約 25%）。x14 的「最多 2 次」與「7 架都領頭」兩個解讀，兩者都偏向選限制換位。
8. 規則選擇（regret 主要來源）：Sonnet 在無特別要求的條目（g1、c2、s7 等）選 gate 的機率約 70%（Haiku 約 45%，其餘多為 rot 或 time）。選 time 且 tenure 很小的話 regret 會到 10-20%。

## 這個預測可以被打臉的地方
- 若兩者遵守率差距 < 5 個百分點，則「模型大小影響遵守」不成立。
- 若 regret 中位數兩者都 < 1%，則環境太寬鬆，結果主要說明 gate 是顯而易見的選擇。
